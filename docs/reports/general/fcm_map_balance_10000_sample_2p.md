`--fast_map_only` 会先完整初始化一次项目上下文，再对每个 seed 执行：

```text
RandomManager(seed) -> fast_forward(player_count - 1) -> generate MapDef -> bake -> analyze -> score
```

这里的 `fast_forward(player_count - 1)` 用于对齐完整开局中 `turn_order` 洗牌对 RNG 的消耗。用前 3 个 seed 对照过完整 `GameEngine.initialize()` 路径，统计结果一致。

## 与报告的对齐判断

大体对齐的部分：

- 初始房屋总数中位数为 5，报告阈值 4-6，中心值对齐。
- 饮料点总数中位数为 6，报告阈值 5-7，中心值对齐。
- 独立街区数中位数为 11，报告阈值 10-12，中心值对齐。
- 道路系统数中位数为 2，报告要求至少 2，中心值对齐。
- 最大空地街区、最大道路系统规模远超最低阈值，说明当前地图通常不缺可建设空间或大路网。

明显不对齐的部分：

- 单道路系统最多房屋中位数为 4，报告阈值是 <=3，只有 24.82% 命中。
- 单道路系统最多饮料中位数为 5，报告阈值是 <=3，只有 25.42% 命中。
- 单道路系统房屋占比失败率高达 90.04%。
- 单街区房屋占比失败率高达 79.84%，说明当前 ratio 阈值比“最多 2 栋”更严格；例如 5 栋房屋中同街区 2 栋会触发 40%，高于当前 2 人阈值 28%。

## 结论

当前随机地图的全局资源数量与报告量级基本一致，但资源集中度，尤其是道路系统集中度，与报告目标明显不一致。

这有两个含义：

1. 如果直接把当前报告阈值作为 hard pass，完全随机生成的通过率只有 0.06%，需要数千次尝试才稳定找到合格地图。
2. 当前 analyzer 把 `RoadGraph` 的连通组件直接视为 road system，而报告中的 road system / route 可能更细。如果不校准定义，道路集中度会成为过强的拒绝条件。

下一步建议：

1. 把 `score` 用作排序目标，而不是只用 hard pass。对于 2 人局，先保留 500-1000 个候选中的最低分地图。
2. 单独复核 road system / route 的定义。如果报告是按路线段、分支、板块道路系统而不是整张连通组件统计，应拆细当前 road system。
3. ratio 阈值建议先降级为 soft penalty，尤其 `max_starting_houses_in_neighborhood_ratio`。否则“单街区 2 栋房屋”在 5 栋总房屋时会被判失败，但这与报告中“最多 2 栋”的直觉检查有冲突。
4. 对 3-5 人分别做 10000 样本，因为玩家数越高，ratio 阈值和道路系统集中度的可通过率可能完全不同。
