# 启发式人机对手：自对弈与调参工具

本文聚焦 selfplay、matrix、tuning matrix、profile variant 和 summary 工具链。

- `tools/run_bot_selfplay.gd` / `tools/run_bot_selfplay.sh` 提供 Bot 自对弈入口，默认运行 StrategyBot，也可用 `--bot=random|greedy|strategy|osla|beam|mcts|strategic` 运行单一 bot，或用 `--bots=random,strategy` 这类 per-player 配置跑固定 matchup；`--profile=<id|path>` 可替换 strategy/osla/beam/mcts/strategic 使用的 `StrategyProfile`；输出每局终局摘要、action counts、trace tail、`bot_config`、`bot_ids`、profile metadata、每位玩家的 `player_milestone_ids` 与可选 JSONL/单局 archive。`action_counts` 只统计 bot 主动提交的命令；`set_price` 这类会被 `auto_advance` 自动补完的 mandatory action 通过 `mandatory_completion_counts`、`untraced_mandatory_completion_counts` 与 `mandatory_completion_tail` 从每步 trace 的 `round_state.mandatory_actions_completed` 差分中记录。每步 trace 还记录 `player_cash_before/after`，match row 汇总 `player_cash_min_seen` / `player_cash_min_after_first_positive` / `player_cash_max_seen`，summary 会输出 `cash_min_seen_avg` / `cash_min_after_first_positive_avg` / `cash_max_seen_avg`，用于区分开局 0、收入形成后现金跌回 0 和正常现金缓冲。match row 也会从每步 explanation / decision trace 聚合 `search_metrics`，记录搜索决策数、预算耗尽次数、模拟次数、展开节点、搜索耗时和 search type counts，便于调 OSLA/Beam/MCTS/StrategicPlan 时区分收益和搜索成本。需要排查候选排序时可传 `--trace-detail=decision` 输出 top candidates、explanation 和 decision trace。
- `tools/run_bot_selfplay_matrix.gd` / `tools/run_bot_selfplay_matrix.sh` 在同一批 seed 下顺序运行多个 `--config=`（例如 `--config=strategy --config=osla --config=mcts --config=strategic --config=random,strategy`），可通过 `--profile=` 对整组配置应用同一 profile，合并 JSONL 并直接生成 summary，作为后续网格/随机调参的最小矩阵入口。MCTS 参数可通过 `--mcts-iterations` / `--mcts-max-depth` / `--mcts-top-k-per-node` / `--mcts-exploration` / `--mcts-min-simulation-budget-ms` / `--mcts-candidate-attempt-multiplier` / `--mcts-root-prior-min-visits-per-child` / `--mcts-enabled-strategies` / `--mcts-config-id` 传入；StrategicPlan 参数可通过 `--strategic-search=beam|mcts`、`--strategic-budget-profile=tuning|play`、horizon/max-plans/rollout budget 和 `--strategic-config-id` 传入。`bot_config` 会带上 MCTS/Strategic 配置片段，避免不同参数组混到同一个 summary bucket；未显式指定时，`strategic` 的自对弈显示为 `strategic-play`。
- `tools/run_bot_tuning_matrix.gd` / `tools/run_bot_tuning_matrix.sh` 在 selfplay matrix 外再包一层 profile sweep：可重复传入 `--profile=`，也可用 `--profile-dir=` 扫描一批候选 profile JSON，或用 `--profile-list=` 读取候选 manifest；每个 profile 都复用同一批 seed/config/matches，最后按 summary 的 `TUNING` objective 输出 bot/profile 行级 `RANK` 和 profile 聚合 `PROFILE_RANK`，并可写出聚合 JSONL / JSON，作为人工调 profile 与后续自动搜索的最小入口。tuning matrix 在未显式传 `--strategic-budget-profile` 时会注入 `tuning`，让 profile/参数 sweep 继续使用低成本预算；真实对局或高预算 smoke 应显式使用 `play`。
- `tools/generate_bot_profile_variants.gd` / `tools/generate_bot_profile_variants.sh` 从一个 base profile 生成最小网格候选：通过重复 `--scale=section.key=factor[,factor]` 按倍数调整数值字段，写出一批带唯一 `id` 的候选 JSON；可选 `--manifest=` 会记录 base profile、输出目录和候选路径，之后可直接交给 `run_bot_tuning_matrix.sh --profile-list=...` 做同 seed/profile sweep。它只生成候选，不自动宣称强度提升。
- `BotSelfplayMatrixTest` 已把自对弈从纯 smoke 拓展为轻量质量门：其中 `strategy/osla/beam` 在 `base_revenue_growth_v1`、seed 12345、target round 4 下做流程 smoke，确认三类 bot wrapper 都能通过同一 matrix 跑通并输出可比较 summary；这只证明搜索入口和矩阵汇总稳定，不要求收入、现金或强度领先。另有 StrategyBot round 8 门槛在同一局中确认两位玩家能形成基础收入、保持收入后现金底线，覆盖基础营销/生产/饮料/招聘里程碑，并进一步确认价格路线会在固定 seed 中自然闭环，双方都完成真实 `set_price` mandatory action、拿到 `first_lower_prices`，并在进入价格路线前形成至少 20 的现金峰值。它仍不用于评价 StrategyBot 强度，只用于在进入 OSLA/Beam/MCTS 或参数搜索前防止核心收入路线退化。
- `tools/summarize_bot_selfplay.gd` / `tools/summarize_bot_selfplay.sh` 读取一个或多个 selfplay JSONL，按 bot/matchup 汇总成功率、平均回合/步数/命令数、action totals、每玩家现金/员工/库存/里程碑/餐厅的 avg/min/max、搜索成本，以及具体 `MILESTONES` 覆盖频次，并输出人类可读摘要与 compact JSON，供 Strategy/OSLA/Beam/MCTS 固定 seed 对照使用。summary 会额外输出 `TUNING` objective：它把成功率、到达回合、收入形成后的现金底线、现金峰值、里程碑覆盖和命令数用显式 weights 汇总为一个调参排序分数；搜索耗时和 budget expired 只保留在 `SEARCH` / `search_delta` / tuning matrix ranking 行里作为预算诊断，不进入 objective score。这个分数只用于同一 seed/profile 矩阵下比较参数组，不是 Bot 行为评分函数。当 summary 中存在 `strategy` 或 `strategy@...` bucket 时，会额外输出以 Strategy 为 baseline 的 `COMPARE` delta，覆盖成功率、回合/步数/命令数、objective score、动作均值、里程碑计数、玩家资源均值和 search cost delta，便于看 OSLA/Beam/MCTS 在给定预算内是否真正改变了行动分布和关键路线覆盖。后续评估“base 关键里程碑规划”时，应优先比较 `milestone_counts` 中缺失或低频的里程碑，而不是只看 `player_milestones` 数量。

这仍只是策略框架和 smoke 验证，还不是完整强度版本。后续应继续扩展难度配置、引入参数搜索产物，并把当前 `StrategyPhasePlanner` / `StrategyRoutePlanner` / `StrategyEmployeePlanner` / `StrategyRecruitPlanner` / `StrategySetupPlanner` / `StrategySupplyPlanner` / `StrategyTrainPlanner` / `StrategyMarketingPlanner` / `StrategyStructurePlanner` / `StrategySupportPlanner` / `StrategyCashPlanner` / `StrategyDinnerPlanner` 继续下钻成更小的阶段策略组件。餐厅放置/移动在 StrategyBot 的 engine 路径下已经优先使用 road graph，但没有 source state 的离线评分仍会保留 anchor 回退。
